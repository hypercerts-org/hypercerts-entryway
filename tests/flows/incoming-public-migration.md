# Test an independent account moving into Entryway

## Prerequisites

Contributors: run `./tests/local.sh fresh-group incoming-public-journey` for a disposable Atmosphere in a Box project. After `prepare` and `up` in an owned project, use `./tests/local.sh incoming-public-journey` instead. Follow the [testing guide](../../docs/testing.md#public-incoming-journey) for setup and cleanup. The journey uses public pages and XRPC, not private fixture commands.

## Inputs

- The project's access projection identifies the standalone stock source, PLC directory and Mailpit; service configuration supplies the Entryway issuer, service DID and destination handle domain.
- Use separate fresh source and destination emails, different handles, generated passwords and a client-held recovery key. The destination email proof is not evidence of source authority.
- If the deployment requires invitations, an administrator issues one separately. The migrant supplies the invite code, not administrator credentials.

## Steps and assertions

1. Create the standalone account. By default, upload a PNG and write a profile referencing it. Use `fresh-group incoming-public-shapes` for that fixture plus an empty repo, a profile without a blob, and a profile with an avatar and two posts. Read back the seeded records and blob bytes, following all list cursors; compare to the seed writes. Take this inventory now: once deactivated, the stock source answers `listRecords` with HTTP 400, so it cannot be read after step 6. Export the CAR before handoff, verify it for the source DID and verify its commit signature against the pre-move PLC signing key. Keep the original source session for the cutover checks.
2. Verify the destination email by OTP. Present a **fresh** code, the source DID and the new handle on the incoming page. Expect a 200 `no-store` preparation and a one-time 32-character arrival code absent from the URL. Retain the handoff and prepared destination endpoint.
3. Obtain PLC confirmation at the source email and sign the prepared operation on the source. Submit to Entryway with a source service JWT bound to `submitPlcOperation`: a wrong arrival code gets 409 `ArrivalExpired`; the correct code with a JWT bound to `createAccount` gets 403. With both correct, expect 200 `no-store`. Before creation, read the PLC head and compare the whole signed operation, including the signature. If the move is abandoned here, Entryway retains its rotation key; arrival expiry does not remove it.
4. Mint a fresh `createAccount` service JWT and send the arrival header, destination handle, password, recovery key and any required invite. Expect 200 `no-store`, the original DID, new handle and `active: false`. Exact replay gets 409 `OperationConflict`; Entryway refuses ordinary `getSession` while paused.
5. In the default blob-bearing shape and the multi-collection shape, first send the paused destination three malformed copies of the verified CAR with the tracked credential. The pinned stock PDS (0.5.36) answers 500 `InternalServerError` when one byte of a record's string field (a post's text, or the profile's display name where the shape has no post) is changed under its CID, 500 `InternalServerError` when the CAR is cut half-way through a block's data, and 400 `InvalidRequest` when the CAR is otherwise whole but has one record's block removed from wherever it sits (the stock export orders blocks by revision and CID, so its final block is not reliably a record). After each refusal, `checkAccountStatus` (inactive, no indexed records, same commit and revision) and the destination's own `getRepo` export must be identical to before the attempt. Then, in every shape, note the destination's `checkAccountStatus` revision and import the verified CAR directly to the prepared destination with tracked credentials; afterwards the revision must differ, which is what distinguishes an imported empty repository from a no-op. Before uploading a referenced blob, require `importedBlobs < expectedBlobs` and its CID in `listMissingBlobs`. Upload the saved bytes; require equal counts and an empty missing list. Check that a repository commit exists but the destination is inactive. Refresh at Entryway (200), activate at the stock destination with the refreshed credential, then verify activated status.
6. Check that the prepared destination is not the source origin. Compare all destination record URIs, values and CIDs and all blob CIDs and bytes with the saved source inventory, not the commit CIDs. The PLC document must name the prepared endpoint and destination handle; the recovery key must lead the rotation list, followed by the approved handoff keys in order. Password `createSession` at Entryway succeeds with either handle or DID and returns the source DID. Deactivate the source; the tracked destination refresh still returns 200 and the original DID.
7. Sign in by destination OTP in a fresh browser context and check the original DID. Authorize the independent SDK by destination handle with visible consent and check the verified DID and Entryway issuer. Read back its DPoP write via the SDK audience-derived link at the prepared PDS. Reload, verify the DID again, refresh successfully and read back another write made with a different access token. Revoke the client session and verify its refresh session disappears from the server's account page, not just from the client. Separately authorize the confidential client and verify its subject, destination audience and write URI.
8. On the standalone deactivated source, the original access token's write gets 401 `AccountDeactivated`. The original refresh token still gets 200 for the source DID with `active: false` and `status: deactivated`. The rotated access token also gets 401 `AccountDeactivated` on write.

The client chooses what to transfer and when to activate. This flow checks the exported fixture state. Source writes after export are not covered by the accepted client-managed contract. The [synthetic migration](external-migration.md) exercises restart boundaries separately.

## Two-node run

Run `./tests/local.sh fresh-group incoming-two-node` (see the [testing guide](../../docs/testing.md#public-incoming-journey-on-two-nodes)). It is one-off evidence for multi-node operation, not a CI gate. The same journey runs on the two-node PostgreSQL profile, once with `entryway` as the first node and once with `entryway-replica`, each with fresh accounts.

1. Steps 2 to 6 alternate nodes. Preparation runs on the first node, the handoff on the second, creation on the first, the tracked refresh on the second, password sign-in on the first and the tracked family refresh on the second. Each stage is pinned with `x-profile-node` and must be answered by the pinned node's instance. Consecutive stages are served by different instances for the same DID.
2. Activation is observed, not pinned: the stock destination forwards `activateAccount` to Entryway through the issuer URL. The ingress receipts must show at least one such request with status 200; the run records which node served it.
3. In step 7, the email-code session and the browser SDK's authorization, including its authorization-code exchange, run on the first node. The SDK then refreshes that grant on the second node at the same issuer. The refresh presents the refresh token the code exchange issued and returns the same subject. A write with the refreshed session succeeds, and the destination still serves every transferred record and blob unchanged beside the two writes. Revocation runs on the first node again and the confidential client on the second.
4. Import and blob upload go only to the destination PDS, so no Entryway node serves them.

Browser requests are pinned by routing only the issuer origin, except the confidential client's authorization: it redirects from the client's origin into the issuer, which a route does not follow, so it is pinned with context-wide extra headers and must make no scripted issuer request. Each pinned request carries a stage tag that the ingress records, so a stage is judged by its own requests, not by when their responses arrived. Consecutive stages must have observed different instance IDs.

While any route is active, Playwright answers every intercepted CORS preflight itself, so no route stage exercises a real preflight. In the single-node journey no route is installed: Entryway answers `/oauth/*` preflights, and the Caddy ingress (`atproto_cors` in `tests/support/entryway-ingress.Caddyfile`) answers `/xrpc/*` and `/.well-known/atproto-did` preflights.

## Failure and restart cases

Run `./tests/local.sh fresh-group incoming-public-failures`, or `./tests/local.sh incoming-public-failures` after `prepare` and `up` (see the [testing guide](../../docs/testing.md#public-incoming-failure-cases)). Each move uses its own fresh source account, source email and destination email. A refusal asserts its status and error name, that the source DID's PLC head is unchanged (nothing published) and that the saved arrival's state and version on the owner's `/incoming` status page are unchanged (nothing claimed). Where a retry with the same arrival code exists, it follows the refusal and succeeds, so a mistyped request cannot pass as a refusal. Cases 8 and 9 save an admission before they are refused, so there the version advances, as each says; they assert instead that the DID's whole PLC audit log is unchanged and that no destination repository exists.

1. **Expired and foreign proofs before admission.** Prepare as in steps 1–2 and sign the handoff. Ask the stock source's `getServiceAuth` for a `submitPlcOperation` token with `exp` two seconds ahead (it accepts any future `exp` up to an hour), check its claims (issuer, method, lifetime, and an audience equal to this Entryway's service DID), wait until it has expired and submit it: 403 `AccountMismatch`, the documented code for a source JWT that fails verification. A service JWT that a second account on the same source minted for the same method gets 409 `ArrivalExpired`, because Entryway selects the arrival by the code and the credential's DID before verifying anything. A fresh JWT then gets 200 `no-store` and the PLC head is exactly the signed handoff.
2. **No recovery key.** Create the destination with only the handle (and any invite): 200 `no-store`, `active: false`. After activation the PLC rotation list equals the approved handoff list exactly. This is the control for step 6's recovery-key ordering.
3. **Lost `createAccount` response.** The client discards the creation response. The exact replay gets 409 `OperationConflict`. On the `/incoming` status page the arrival is paused and pending; the owner asks for a fresh code and posts `/incoming/recover` with it and the current version: 200 `no-store`, new credentials for the same DID. The stock destination still accepts the earlier access token until it expires (about five minutes), as documented; Entryway refuses the earlier refresh token at `refreshSession` and the earlier access token at `activateAccount` with 400 `ExpiredToken`. The replacement refresh token rotates (200), and its access token imports, uploads the blob and activates through the stock destination; the destination then serves the source inventory.
4. **Pending account before activation.** This runs within step 3, after the replay conflict and before recovery. With the owner's verified session from preparation, `/account` answers 409 "Migration in progress" with the pending notice ("This account is part of an unfinished incoming migration"), and console posts (`status`, `handle`) with this browser's CSRF field get the same 409 page; the arrival stays paused and pending. Authorizing the browser SDK by destination handle cannot start: Entryway's `/.well-known/atproto-did` answers 404 for a provisioning account, so the client shows its own error; after activation (step 2) the same endpoint answers 200 with the DID. Email-code sign-in is documented to succeed, create a session and show the pending page. Today `/auth/verify` answers 404 with the "Unable to continue" page ("Account not found") and commits no session (`/incoming` still redirects to `/login`), both at `/login` and after the OAuth email-code step by DID; no consent form is offered and the browser never returns to the client. Ordinary tests assert this observed page. The documented sign-in, and for OAuth the pending notice with no consent, are asserted in two separate tests marked as known failures. The cause: `assertLoginEmail` (`src/features/account-settings/security.mjs`) calls `syncBoundAccountEmailVerification`, whose `account()` lookup (`src/database/drizzle/account-authority.mjs`) refuses `provisioning` accounts. The OAuth consent guard (`src/features/oauth-authorization/consent.mjs`) is not exercised until that sign-in defect is fixed. From reading `src/features/email-login/routes.mjs`, a single bound provisioning account then goes to the signup page's pending notice before consent, so the guard is reached only from the account chooser. These are the pending-arrival guards as they are today; a single enforced guard is decided follow-up work.
5. **Destination email taken after preparation.** Prepare a second move, then the same verified owner signs up an ordinary Entryway account with that email in another browser. The signed handoff gets 409 `EmailNotAvailable`; nothing is published or claimed. A new preparation for that email also gets 409 `EmailNotAvailable` and leaves the earlier arrival's state and version unchanged. The existing account keeps its DID, handle, verified email and PLC head, and its handle still resolves to its DID. No same-code success exists for this refusal.
6. **Restart between admitted steps.** A third move runs as two browser phases. Phase one prepares, signs the handoff and submits it with a 20-second source JWT: 200 and the PLC head is the handoff. The controller restarts the Entryway service and waits until it is healthy. Phase two signs in again by email code, finds the arrival still "handoff published" with a fresh code renews its arrival code (`/incoming/renew`, 200 `no-store`, a new code), and replays the handoff exactly: with the superseded code 409 `ArrivalExpired`; with the renewed code and the now-expired phase-one JWT 200 `{}`, because an already admitted method is not re-verified, and the PLC head is still the one handoff. The first `createAccount` body is sent first with a JWT bound to `submitPlcOperation`: 403 `AccountMismatch`, with the PLC head and the saved arrival unchanged. An exact replay of a recorded admission would succeed without a credential, so this shows phase one recorded no creation admission. The same body with a fresh `createAccount` JWT, password and recovery key then gets 200: a new admission. The controller checks that the Entryway container's start time changed across the restart. Import, activation, inventory comparison and recovery-key ordering complete the move. This is a restart between admitted steps, not an interruption during provisioning.

7. **Handle or DID already hosted at the target.** This runs after step 5 and reuses its ordinary account, and the DID that step 3 migrated in and activated. A fresh owner prepares a fresh source account with a free handle, then asks for three more preparations, each with a fresh code: one with the ordinary account's handle gets 409 `HandleNotAvailable`; one for the ordinary account's DID and one for the migrated DID each get 409 `IdentityConflict`. Each refusal leaves the owner's earlier arrival as it was. A second ordinary account then signs up with the prepared handle, and the signed handoff gets 409 `HandleNotAvailable`; nothing is published or claimed. The ordinary accounts keep their DID, PLC head and handle resolution (the one still signed in also its console and email), and the destination still hosts the migrated repository. No same-code success exists for these refusals.
8. **Foreign PLC head between handoff and creation** (`tests/browser/incoming-public-identity.spec.mjs`). After the handoff is published, the source user changes their handle at the stock source (`updateHandle`), which publishes a source-signed operation on top of the handoff that keeps its rotation list, Entryway's key included. `createAccount` with a fresh JWT then gets 409 `OperationRecoveryRequired`: the creation admission is saved (the arrival's version advances, its state stays "handoff published"), but provisioning only continues over the saved handoff or the saved move. The exact replay and the owner's `/incoming/resume` get the same refusal. Each time, the DID's PLC audit log is exactly as the source left it, the destination hosts no repository for the DID (`getRepoStatus` 400 `RepoNotFound`) and the destination handle does not resolve. The user then removes Entryway's rotation key through the source (`requestPlcOperationSignature`, `signPlcOperation` with the earlier rotation list, `submitPlcOperation`), the documented way out of an abandoned handoff; creation is still refused the same way and nothing is added after it.
9. **Superseded signed handoff.** The source signs the prepared handoff, then the user changes their handle at the source, so the signed handoff's predecessor is no longer the head. A handoff signed again on the new head gets 400 `InvalidPlcOperation`, because its predecessor is not the one saved at preparation; nothing is claimed. The superseded handoff itself gets 409 `OperationRecoveryRequired`: it is never published, but its claim, replay binding and signed bytes were saved before dispatch, so the version advances while the state stays "prepared". Its exact replay and a `createAccount` get the same refusal and publish nothing. The claim now holds the DID at this Entryway: `/incoming/cancel` gets 409 `OperationRecoveryRequired` and a new preparation for the DID gets 409 `OperationPending`, so the user cannot start this move again without the [operator recovery](../../docs/shared-operations.md#supported-operator-recovery). The source keeps full authority, since nothing was published.

Covered elsewhere: an import with a withheld blob (step 5 of the journey), a lost `createAccount` response and its replay (case 3), and a restart between admitted steps (case 6). Applied-but-lost destination creation and deactivation are covered by `./tests/local.sh incoming-arrival-live`.

Left to contract tests, because a public client cannot provoke them:

- **A continuation from a claim that lost its lease.** A lease exists only while one request runs: the request acquires it and renews it every 30 seconds until it returns (`src/accounts/operation-ownership.ts`, `run`), and `OPERATION_LEASE_MS` is at least five seconds (`src/config.mjs`). A client can neither keep a request open past expiry nor stall the worker; that takes pausing an Entryway process mid-request, and the successor then meets the open dispatch receipt and needs operator approval with the administrator credential. Two concurrent requests to two nodes contend for the lease (`OperationPending`) rather than lose it. The contract tests cover it: a stale owner cannot finish activation while its successor resumes the claim (`tests/contracts/incoming-activation.test.mjs`, "a stale owner cannot finish activation"); every arrival storage write refuses a stale or expired owner with `OperationLeaseLost` and changes nothing (`tests/contracts/incoming-arrival-storage.test.mjs`, "persisted arrival ownership"); a paused PostgreSQL worker is fenced after another process takes over (`tests/contracts/operation-ownership.test.mjs`); and recovery after a killed worker with a held lease (`tests/contracts/incoming-arrival-reconciliation.test.mjs`, cut `lease-takeover`).
- **A DID that becomes hosted after preparation** (`IdentityConflict` at handoff). Publicly, a DID only becomes hosted here through another arrival, whose claim refuses this one with `OperationPending` until its move is published; after that the DID's signing key is the destination's, so this arrival's source JWT fails first with 403 `AccountMismatch`. The handoff refusal is covered by `src/features/external-migration/incoming-xrpc.test.mjs` ("admission refuses IdentityConflict with 409 when it arose since preparation").

**Known limitation: abandoned handoff.** If the handoff is published and the destination account is never created, Entryway's rotation key stays on the DID, after the source's keys. Arrival expiry and local cleanup do not remove it; the user can remove it through the source PDS with `requestPlcOperationSignature` and `signPlcOperation` (see [cancellation](../../docs/incoming-migration.md#cancellation)). A supported cleanup is known follow-up work. These cases leave no DID with Entryway's key behind: every published handoff above is completed, except case 8's, whose user removes the key through the source as described.
