# Test an independent account moving into Entryway

## Prerequisites

Contributors: run `./tests/local.sh fresh-group incoming-public-journey` for a disposable Atmosphere in a Box project. After `prepare` and `up` in an owned project, use `./tests/local.sh incoming-public-journey` instead. Follow the [testing guide](../../docs/testing.md#public-incoming-journey) for setup and cleanup. The journey uses public pages and XRPC, not private fixture commands.

## Inputs

- The project's access projection identifies the standalone stock source, PLC directory and Mailpit; service configuration supplies the Entryway issuer, service DID and destination handle domain.
- Use separate fresh source and destination emails, different handles, generated passwords and a client-held recovery key. The destination email proof is not evidence of source authority.
- If the deployment requires invitations, an administrator issues one separately. The migrant supplies the invite code, not administrator credentials.

## Steps and assertions

1. Create the standalone account. By default, upload a PNG and write a profile referencing it. Use `fresh-group incoming-public-shapes` for that fixture plus an empty repo, a profile without a blob, and a profile with an avatar and two posts. Read back the seeded records and blob bytes, following all list cursors; compare to the seed writes. Take this inventory now: once deactivated, the stock source answers `listRecords` with HTTP 400, so it cannot be read after step 6. Export the CAR before handoff, verify it for the source DID and verify its commit signature against the pre-move PLC signing key. Keep the original source session for the cutover checks.
2. Verify the destination email by OTP. Present a **fresh** code, the source DID and the new handle on the incoming page. Expect a 200 `no-store` preparation and a one-time 32-character arrival code absent from the URL. Retain the handoff and prepared destination endpoint.
3. Obtain PLC confirmation at the source email and sign the prepared operation on the source. Submit to Entryway with a source service JWT bound to `submitPlcOperation`: a wrong arrival code gets 409 `ArrivalExpired`; the correct code with a JWT bound to `createAccount` gets 403. With both correct, expect 200 `no-store`. Before creation, read the PLC head and compare the whole signed operation, including the signature. If the move is abandoned here, Entryway retains its rotation key; arrival expiry does not remove it.
4. Mint a fresh `createAccount` service JWT and send the arrival header, destination handle, password, recovery key and any required invite. Expect 200 `no-store`, the original DID, new handle and `active: false`. Exact replay gets 409 `OperationConflict`; Entryway refuses ordinary `getSession` while paused.
5. In the default blob-bearing shape and the multi-collection shape, first send the paused destination three malformed copies of the verified CAR with the tracked credential. The pinned stock PDS (0.5.36) answers 500 `InternalServerError` when one byte of a record's string field (a post's text, or the profile's display name where the shape has no post) is changed under its CID, 500 `InternalServerError` when the CAR is cut half-way through a block's data, and 400 `InvalidRequest` when the CAR ends cleanly before its final record block. After each refusal, `checkAccountStatus` (inactive, no indexed records, same commit and revision) and the destination's own `getRepo` export must be identical to before the attempt. Then, in every shape, note the destination's `checkAccountStatus` revision and import the verified CAR directly to the prepared destination with tracked credentials; afterwards the revision must differ, which is what distinguishes an imported empty repository from a no-op. Before uploading a referenced blob, require `importedBlobs < expectedBlobs` and its CID in `listMissingBlobs`. Upload the saved bytes; require equal counts and an empty missing list. Check that a repository commit exists but the destination is inactive. Refresh at Entryway (200), activate at the stock destination with the refreshed credential, then verify activated status.
6. Check that the prepared destination is not the source origin. Compare all destination record URIs, values and CIDs and all blob CIDs and bytes with the saved source inventory, not the commit CIDs. The PLC document must name the prepared endpoint and destination handle; the recovery key must lead the rotation list, followed by the approved handoff keys in order. Password `createSession` at Entryway succeeds with either handle or DID and returns the source DID. Deactivate the source; the tracked destination refresh still returns 200 and the original DID.
7. Sign in by destination OTP in a fresh browser context and check the original DID. Authorize the independent SDK by destination handle with visible consent and check the verified DID and Entryway issuer. Read back its DPoP write via the SDK audience-derived link at the prepared PDS. Reload, verify the DID again, refresh successfully and read back another write made with a different access token. Revoke the client session and verify its refresh session disappears from the server's account page, not just from the client. Separately authorize the confidential client and verify its subject, destination audience and write URI.
8. On the standalone deactivated source, the original access token's write gets 401 `AccountDeactivated`. The original refresh token still gets 200 for the source DID with `active: false` and `status: deactivated`. The rotated access token also gets 401 `AccountDeactivated` on write.

The client chooses what to transfer and when to activate. This flow checks the exported fixture state. Source writes after export are not covered by the accepted client-managed contract. The [synthetic migration](external-migration.md) exercises restart boundaries separately.

## Failure and restart cases

Run `./tests/local.sh fresh-group incoming-public-failures`, or `./tests/local.sh incoming-public-failures` after `prepare` and `up` (see the [testing guide](../../docs/testing.md#public-incoming-failure-cases)). Each move uses its own fresh source account, source email and destination email. A refusal asserts its status and error name, that the source DID's PLC head is unchanged (nothing published) and that the saved arrival's state and version on the owner's `/incoming` status page are unchanged (nothing claimed). Where a retry with the same arrival code exists, it follows the refusal and succeeds, so a mistyped request cannot pass as a refusal.

1. **Expired and foreign proofs before admission.** Prepare as in steps 1–2 and sign the handoff. Ask the stock source's `getServiceAuth` for a `submitPlcOperation` token with `exp` two seconds ahead (it accepts any future `exp` up to an hour), check its claims, wait until it has expired and submit it: 403 `AccountMismatch`. A service JWT that a second account on the same source minted for the same method gets 409 `ArrivalExpired`, because Entryway selects the arrival by the code and the credential's DID before verifying anything. A fresh JWT then gets 200 `no-store` and the PLC head is exactly the signed handoff.
2. **No recovery key.** Create the destination with only the handle (and any invite): 200 `no-store`, `active: false`. After activation the PLC rotation list equals the approved handoff list exactly. This is the control for step 6's recovery-key ordering.
3. **Lost `createAccount` response.** The client discards the creation response. The exact replay gets 409 `OperationConflict`. On the `/incoming` status page the arrival is paused and pending; the owner asks for a fresh code and posts `/incoming/recover` with it and the current version: 200 `no-store`, new credentials for the same DID. The stock destination still accepts the earlier access token until it expires (about five minutes), as documented; Entryway refuses the earlier refresh token at `refreshSession` and the earlier access token at `activateAccount` with 400 `ExpiredToken`. The replacement refresh token rotates (200), and its access token imports, uploads the blob and activates through the stock destination; the destination then serves the source inventory.
4. **Pending account before activation**, between steps 3 and 4 above. With the owner's verified session from preparation, `/account` answers 409 "Migration in progress" with the pending notice ("This account is part of an unfinished incoming migration"), and console posts (`status`, `handle`) with this browser's CSRF field get the same 409 page; the arrival stays paused and pending. Authorizing the browser SDK by destination handle cannot start: Entryway's `/.well-known/atproto-did` answers 404 for a provisioning account, so the client shows its own error. By DID, the authorization reaches Entryway's email-code step and, after the code, offers no consent form and never returns to the client. The documented sign-in behaviour, that email-code sign-in succeeds, creates a session and shows the pending page, is asserted in a test marked as a known failure: today `/auth/verify` answers 404 "Account not found" (title "Unable to continue") for both `/login` and the OAuth sign-in, and commits no session, because the login resolution syncs email verification through an account lookup that refuses `provisioning` accounts. The OAuth check therefore shows consent refused at sign-in, not the pending page. These are the pending-arrival guards as they are today; a single enforced guard is decided follow-up work.
5. **Destination email taken after preparation.** Prepare a second move, then the same verified owner signs up an ordinary Entryway account with that email in another browser. The signed handoff gets 409 `EmailNotAvailable`; nothing is published or claimed. A new preparation for that email also gets 409 `EmailNotAvailable`. The existing account keeps its DID, handle, verified email and PLC head, and its handle still resolves to its DID. No same-code success exists for this refusal.
6. **Restart between admitted steps.** A third move runs as two browser phases. Phase one prepares, signs the handoff and submits it with a 20-second source JWT: 200 and the PLC head is the handoff. The controller restarts the Entryway service and waits until it is healthy. Phase two signs in again by email code, finds the arrival still "handoff published" with a fresh code renews its arrival code (`/incoming/renew`, 200 `no-store`, a new code), and replays the handoff exactly: with the superseded code 409 `ArrivalExpired`; with the renewed code and the now-expired phase-one JWT 200 `{}`, because an already admitted method is not re-verified, and the PLC head is still the one handoff. The first `createAccount` then follows with a fresh method-bound JWT, password and recovery key: a new admission, not a replay, since phase one recorded none. Import, activation, inventory comparison and recovery-key ordering complete the move. This is a restart between admitted steps, not an interruption during provisioning.

**Known limitation: abandoned handoff.** If the handoff is published and the destination account is never created, Entryway's rotation key stays on the DID, after the source's keys. Arrival expiry and local cleanup do not remove it; the user can remove it through the source PDS with `requestPlcOperationSignature` and `signPlcOperation` (see [cancellation](../../docs/incoming-migration.md#cancellation)). A supported cleanup is known follow-up work. These cases leave no such DID behind: every published handoff above is completed.
